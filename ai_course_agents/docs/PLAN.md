Изменения относительно исходного плана:
- Этап 0: ноутбук практики вынесен в отдельный uv-проект `practice/`. Причина: `litellm>=1.84` (рекомендован ADK) требует `openai<3`, а `openai-agents` ноутбука требует `openai>=3`. В сервисе стоят `litellm` 1.105 и `openai` 2.54.
- Этап 1:
  - добавлены инструменты `top_brands` и `rank_by_distance` (уточнения «какой из них ближе»);
  - `geocode` без номера дома даёт центр улицы, а при совпадении нескольких улиц — список `other_streets`;
  - цена считается с учётом кэша DeepSeek (`PRICE_CACHED_RUB`): схемы инструментов с перечнем 82 видов — около 3.6 тыс. токенов на запрос, но со второго запроса они в основном берутся из кэша;
  - добавлены тесты слоя базы `tests/test_repo.py`.
- Этап 2:
  - **Гибридный поиск вместо чисто векторного.** Векторы из Qdrant плюс лексика по основам слов, объединение взвешенным RRF (вес лексики 2). Только векторы проваливали однословные запросы («пельмени», «шаурма», «плов»): маленькая модель даёт им сходство около 0.45, а короткие описания вроде «Паб «Визирь»» становятся «хабами».
  - **Модель — MiniLM-L12** (`paraphrase-multilingual-MiniLM-L12-v2`). Кандидаты: MiniLM, mpnet-base, potion-128M; `rubert-tiny2` в fastembed нет. Оценка `scripts/eval_search.py`, 12 запросов, только общепит:

    | модель, режим | P@5 | hit@1 | индекс | поиск |
    |---|---|---|---|---|
    | MiniLM, только векторы | 0.62 | 0.67 | 59 с | |
    | **MiniLM, гибрид** | **0.92** | **1.00** | 59 с | ≈65 мс |
    | mpnet, гибрид | 0.92 | 1.00 | 208 с | |
    | potion, гибрид | 0.83 | 1.00 | 14 с | |

  - **Скорость на CPU.** Эмбеддинг запроса занимает 3 мс. Из ≈65 мс поиска 60 мс уходит на фильтр embedded-Qdrant: он проверяет условия питоном по всем точкам, а серверный Qdrant делал бы это по индексу. Это осознанный компромисс ради работы без сервера.
  - **Обогащение через DeepSeek.** 466 заведений без кухни: у 373 есть догадка, у 93 — `null`; ≈2.5 мин, около рубля. Строгая P@5 (только факты базы) 0.92 → 0.85, P@5 с учётом догадок 0.92 → 0.97. Охват растёт («Осака», «Самовар», «Чайхана»), точность по проверенным данным немного падает. Чтобы смягчить это, совпадение в догадке весит вдвое меньше, чем совпадение в фактах.
  - Исправлена ошибка: синонимы в названии вида («фастфуд, шаурма, бургерная») попадали в описание каждого места этого вида.
  - Hugging Face с этой сети зависает при загрузке через протокол Xet, поэтому в `search/vector.py` выставлено `HF_HUB_DISABLE_XET=1`.
  - Новая задача для этапа 3: DeepSeek может оборвать соединение посреди потока (`Connection closed`). Нужны повторные попытки и понятное сообщение пользователю.
- Этап 3:
  - **Структура веб-слоя.** `web/db.py` (пользователи и чаты), `security.py` (bcrypt, JWT), `deps.py` (сервисы и текущий пользователь), `auth.py`, `chats.py`, `events.py` (разбор событий ADK), `stream.py` (SSE), `app.py` (lifespan).
  - **Сессии.** `SqliteSessionService` из ADK: `get_session` сам фильтрует по `user_id`, так что изоляция встроена. Чужой чат → 404 (не 403, чтобы не подтверждать, что чат существует).
  - **Гардрейл.** Колбэк `before_model_callback`: отказ без вызова LLM (0 токенов, около 15 мс). Срабатывает только на явные посторонние просьбы, уточнения вроде «а второй?» пропускает.
  - **Обрезка истории.** Модель видит последние 6 реплик пользователя; резать можно только по границе хода, иначе останется `function_call` без ответа.
  - **Сбои DeepSeek.** `num_retries=2` в LiteLLM повторяет запрос до начала потока; ошибки разбираются по цепочке исключений и превращаются в понятное SSE-событие `error`.
  - **Остановка ответа.** Клиент разорвал соединение → прогон отменяется. Найдены и исправлены две ошибки:
    - запись в журнал прерывалась той же отменой — помогла защищённая область `anyio.CancelScope(shield=True)`;
    - оборванный вопрос оставался в истории без ответа, и следующий ответ отвечал на оба. Теперь ход закрывается служебной репликой, а «висящие» вызовы инструментов получают результат-ошибку.
  - **Проверка** `scripts/api_demo.py`:
    - поток стартует через 0.01 с;
    - контекст и уточнения работают;
    - гардрейл отвечает за 0 ₽;
    - bob получает 404 на чат alice;
    - два пользователя обслуживаются параллельно.
  - curl в Git Bash портит кириллицу в `-d`, поэтому для проверки написан клиент на httpx.
  - Известная неточность: токены оборванного запроса не учитываются — DeepSeek присылает `usage` только в конце ответа.
- Этап 4:
  - **Фронтенд без сборки.** `static/index.html`, `styles.css`, ES-модули `api.js` (fetch + разбор SSE), `map.js` (Leaflet), `render.js` (сообщения), `app.js` (состояние). Библиотеки с cdnjs, версии зафиксированы.
  - **«Ход мысли».** Главное в нём — шаги агента по-русски, с аргументами, результатом и временем. Размышления DeepSeek (по-английски) видны вживую, пока агент думает; после ответа блок сворачивается, а размышления остаются под ссылкой «размышления модели (англ.)». Текст модели перед вызовом инструмента («сейчас найду…») переносится в размышления.
  - **Карта.** Метки обновляются прямо во время ответа. Клик по жирному названию места в ответе открывает его метку. Точка, от которой считались расстояния, отмечена значком 📍.
  - **Найдено скриншотами из настоящего браузера** (`scripts/ui_check.py`, Playwright + Edge) и исправлено:
    - плитки CARTO без ключа показывают водяной знак — перешли на плитки OSM, тёмная тема сделана CSS-фильтром;
    - в мобильной вёрстке карта открывалась без меток (масштаб подгонялся, пока панель была скрыта);
    - служебная пометка об остановке в истории выглядела как текст ответа;
    - после «Стоп» «Ход мысли» не сворачивался;
    - кухня в ответах выходила латинскими тегами (`japanese;russian`).

## Контекст

Преподаватель усложнил задание из `week2/assignment.md`: вместо скрипта с `check.py` нужен работающий веб-сервис на Python + ADK над базой мест Ростова (`week2/practice/poi.sqlite`, 8860 мест). Оцениваются **UX** и **архитектурные решения**. Обязательные требования:

1. Фронтенд с формой вопроса.
2. Асинхронный многопользовательский бэкенд с авторизацией.
3. SSE: видно, как думает агент.
4. Учёт контекста диалога.
5. Семантический поиск через векторную БД: запрос «пельмени» находит рестораны, близкие по смыслу.

Из исходного задания берём инженерную часть: инструменты со схемами и описаниями для модели, лимит шагов, ошибки инструментов как наблюдения, журнал JSONL, учёт токенов и цены. Сам `check.py` и A/B-тест не делаем.

Принятые решения:
- LLM: DeepSeek (`deepseek-flash`) через LiteLLM.
- Эмбеддинги считаются локально.
- Описания для поиска собираются из словаря кухонь плюс разового обогащения через DeepSeek.
- Фронтенд без сборки, раздаётся самим FastAPI.
- Запуск только через `uv run`, без Docker.

Ограничения, проверенные на практике и в коде ADK 2.9.2:
- DeepSeek не поддерживает `response_format: json_schema`, поэтому `output_schema` у агента не используем.
- В режиме размышлений DeepSeek не принимает `tool_choice="required"`.
- `litellm` и `sqlalchemy` не установлены. Историю диалогов храним в `google.adk.sessions.sqlite_session_service.SqliteSessionService`: ему хватает уже установленного `aiosqlite`.
- Размышления модели приходят как `Part(thought=True)`; в режиме `StreamingMode.SSE` это частичные события. Их и показываем пользователю как «ход мысли».

## Архитектура

```
Браузер (HTML + JS + Leaflet) ──fetch/SSE──► FastAPI (uvicorn, async)
                                          ├─ auth: JWT в httpOnly-cookie, пароли bcrypt
                                          ├─ chats: список / создание / удаление / история
                                          └─ POST /api/chats/{id}/messages → поток SSE
                                                 │
                                    ADK Runner.run_async(user_id, session_id, StreamingMode.SSE)
                                                 │
                     LlmAgent(LiteLlm "openai/deepseek-flash", api_base=api.deepseek.com)
                       ├─ инструменты: SQL по poi.sqlite (aiosqlite) + semantic_search (Qdrant)
                       ├─ колбэки: гардрейл, обрезка истории, журнал JSONL
                       └─ SqliteSessionService (data/sessions.sqlite): контекст диалога
```

Ключевые архитектурные решения (их обоснование пойдёт в `docs/ARCHITECTURE.md`):

- **Своё приложение FastAPI вокруг `Runner`, а не `adk web`.** У `adk web` нет авторизации, и он навязывает свою схему URL. Обработчик `/run_sse` из `google/adk/cli/api_server.py` берём как образец.
- **Многопользовательность.**
  - `user_id` берётся только из JWT, никогда из тела запроса.
  - ADK сам ограничивает сессии по `user_id`, поэтому чужую сессию прочитать нельзя.
  - Блокировка на каждый чат не даёт запустить два прогона в одной сессии одновременно (иначе история перепутается).
  - Глобальный семафор ограничивает число одновременных запросов к LLM.
  - Код, нагружающий CPU (эмбеддинг запроса), выполняется через `asyncio.to_thread`.
- **Векторная БД — Qdrant в embedded-режиме** (`qdrant-client`, хранение в `data/qdrant/`, отдельный сервер не нужен).
  - Есть фильтры по полям записи (`kind`) и **геофильтр** (`geo_radius`), так что работает запрос «пельмени рядом с Садовой».
  - Эмбеддинги считает `fastembed` (ONNX, без torch), мультиязычная модель. Первая кандидатура — `paraphrase-multilingual-MiniLM-L12-v2`, окончательный выбор по оценке на этапе 2.
- **Эмбеддинги на CPU (машина без GPU).**
  - Выбран `fastembed`, а не `sentence-transformers`: нет PyTorch (установка примерно 100 МБ вместо 1–2 ГБ), и на CPU он быстрее.
  - Индекс строится один раз (оценка 20–60 с на 6–8 тысяч описаний) и хранится на диске.
  - Эмбеддинг одного запроса занимает порядка 10–30 мс против 1–5 с на каждый вызов LLM, то есть меньше 1% времени ответа.
  - Запросы считаются в `asyncio.to_thread`, повторы берутся из LRU-кэша.
  - Если замер на этапе 2 окажется плохим, переходим на `cointegrated/rubert-tiny2`: модель примерно в 4 раза меньше.
  - У DeepSeek нет API для эмбеддингов, поэтому считаем локально.
- **Что из результата инструмента попадает в контекст модели.**
  - Модель получает компактную таблицу: до 10 строк, только нужные поля. Это урок задачи 2 и ошибок прошлых лет: «не класть в ответ весь запрос».
  - Координаты мест идут в том же ответе. Обработчик SSE вынимает из него список `places` и отправляет фронтенду отдельным событием для карты.
- **Контекст диалога.**
  - Историю хранит `SqliteSessionService`.
  - Последние найденные места инструменты кладут в `tool_context.state["last_places"]`, поэтому работает «а какой из них ближе к Пушкинской?».
  - `before_model_callback` обрезает историю до последних N реплик пользователя: цена обрезки — тема задачи 5.
- **Надёжность.**
  - `RunConfig(max_llm_calls=12)`; при `LlmCallsLimitExceededError` клиент получает SSE-событие `error` с понятным текстом (задача 6).
  - Инструменты не бросают исключения, а возвращают `{"error": ...}`: ошибка становится наблюдением для модели.
  - Гардрейл без LLM отсекает явно посторонние просьбы (стихи, переводы, математика) до вызова модели (задача 8). Уточнения вроде «а из них?» он не блокирует.
- **Наблюдаемость.**
  - На каждый прогон пишется строка в `data/runs/YYYY-MM-DD.jsonl`: пользователь (хеш), вопрос, вызовы инструментов, токены из `usage_metadata`, цена, задержка, итог.
  - Токены и цена ответа видны и в интерфейсе.

## Интерфейс (UX)

- **Вход.** Экран входа и регистрации.
- **Слева** — список чатов: новый чат, удаление, заголовок по первому вопросу.
- **В центре** — чат:
  - Ответы рендерятся из markdown через `marked` и `DOMPurify`.
  - Над каждым ответом сворачиваемый блок **«Ход мысли»**: размышления модели потоком, затем шаги «🔧 semantic_search("пельмени") → нашла 8 мест · 0.4 с». Пока агент работает, блок раскрыт.
  - Ответ печатается потоком, а не появляется целиком.
  - Есть кнопка «Стоп» (AbortController; на сервере прогон отменяется при отключении клиента).
  - Под ответом — токены и цена.
- **Справа** — карта Leaflet: метки мест из последних результатов инструментов, клик по метке открывает карточку места, клик по месту в ответе подсвечивает его на карте.
- **Пустой чат** показывает подсказки-примеры:
  - «Где поесть пельменей?»
  - «Ближайшая аптека к Белорусской, 44 и до скольки работает»
  - «Сколько в городе круглосуточных аптек?»
  - «Суши рядом с Пушкинской»
- **Мобильная вёрстка:** карта сворачивается во вкладку.
- **Ошибки** (лимит шагов, сеть, сессия истекла) показываются понятными сообщениями, а не трассировкой.
- **Библиотеки** с cdnjs/unpkg, версии зафиксированы, сборки нет.

## Ход работ

Работаю по этапам. **После каждого этапа останавливаюсь:** показываю результат и что проверить, делаю коммит и жду команды «дальше». Внутри этапа шаги идут по порядку; у каждого шага указано, что получится и как это увидеть.

### Этап 0. Подготовка (≈15 мин)
1. `uv add litellm qdrant-client fastembed bcrypt pyjwt sse-starlette`; `uv add --dev pytest pytest-asyncio`.
2. Создать каркас пакета `src/ai_course_agents/` по разделу «Структура проекта»: пустые модули с докстроками.
3. `config.py`: чтение `.env` (`DEEPSEEK_API_KEY`, `MODEL=deepseek-flash`, `JWT_SECRET`, пути к `poi.sqlite` и `data/`). Добавить `.env.example`. Дописать в `.gitignore` папку `ai_course_agents/data/`.
4. Пробный вызов `LiteLlm` к DeepSeek одной строкой, чтобы убедиться, что связка ADK → LiteLLM → DeepSeek работает.

**Контрольная точка 0:** `uv run python -c "..."` печатает ответ DeepSeek через ADK. Коммит «Каркас MVP и зависимости».

### Этап 1. Агент в консоли, без веба (≈1–1.5 ч)
1. `poi/repo.py`: асинхронные функции над `poi.sqlite`:
   - `search_places`, `count_places`, `geocode` (логика `address_point`), `nearest_places`, `place_details`;
   - `distance_m`, `table` перенесены из `sdk_tasks`.
2. `agent/tools.py`: инструменты ADK поверх репозитория.
   - Описания по шаблону задачи 4: что делает, когда звать, когда НЕ звать, что вернёт, Args.
   - `kind` — перечень значений (урок задачи 3).
   - Ошибки возвращаются как `{"error": ...}`.
   - Найденные места кладутся в `tool_context.state["last_places"]`.
3. `agent/agent.py`: `LlmAgent` и `LiteLlm`, системная инструкция (не выдумывать числа, порядок цепочки).
4. Консольная обвязка `uv run python -m ai_course_agents.agent "вопрос"`: печатает события ADK — 💭 размышления, 🔧 вызовы, 📦 результаты, итоговый ответ, токены.

**Контрольная точка 1:** запускаешь консольный скрипт с вопросами «Сколько круглосуточных аптек?» (ответ 19) и «Белорусская, 44 — ближайшая аптека и часы» (Лаки Фарма, 08:00–21:00). Видны размышления и цепочка вызовов. Коммит «Агент ADK с инструментами над базой».

### Этап 2. Семантический поиск (≈1.5–2 ч)
1. `search/cuisine.py`: словарь кухонь OSM → русские слова и блюда; функция «место → текст описания».
2. `search/enrich.py`: разовое обогащение ~600 заведений без кухни через DeepSeek, пачками по 50.
   - Сначала показываю 10 примеров на проверку, потом запускаю полностью (около рубля).
   - Результат пишется в `data/enrichment.json` (коммитится), у каждой записи пометка `source: "llm_guess"`.
3. `search/index.py`: эмбеддинги через `fastembed` → коллекция Qdrant (`data/qdrant/`), с полями `kind`, адресом и геоточкой.
4. Оценка: 10 запросов («пельмени», «суши», «шаурма», «кофе с собой», «грузинская кухня», «пицца»…) с ожидаемыми местами.
   - Метрика hit@5 для двух моделей: MiniLM и rubert-tiny2.
   - Замер скорости на твоём CPU: время построения индекса и задержка запроса (p50/p95).
   - Сравниваю и выбираю модель.
5. `search/vector.py` и инструмент `semantic_search(query, near?, radius?)` подключаются к агенту.

**Контрольная точка 2:** таблица hit@5 и скорости по моделям. В консоли «Где поесть пельменей?» → агент зовёт `semantic_search`, в ответе подходящие заведения. Коммит «Семантический поиск: Qdrant + fastembed».

### Этап 3. Бэкенд FastAPI (≈2 ч)
1. `web/app.py`: фабрика приложения и lifespan (открывает базы, сервис сессий, Qdrant, модель эмбеддингов один раз на процесс).
2. `web/auth.py`: регистрация, вход, выход, `/me`. Пользователи в `data/app.sqlite`, пароли bcrypt, JWT в httpOnly-cookie.
3. `web/chats.py`: список, создание, удаление чатов, история сообщений из `SqliteSessionService`. Чужой чат → 404.
4. `web/stream.py`: `POST /api/chats/{id}/messages` → поток SSE.
   - Типы событий: `thinking`, `tool_call`, `tool_result`, `places`, `token`, `usage`, `done`, `error`.
   - При отключении клиента прогон отменяется.
5. Надёжность:
   - блокировка на чат и глобальный семафор LLM;
   - `max_llm_calls=12`;
   - гардрейл (`before_model_callback`) и обрезка истории;
   - журнал прогонов в `data/runs/*.jsonl`.

**Контрольная точка 3:** запуск `uv run uvicorn ...`. Показываю сценарий через `curl`: регистрация → вход → создание чата → `curl -N` с живым потоком событий. Второй пользователь получает 404 на чужой чат. Коммит «Бэкенд: auth, чаты, SSE».

### Этап 4. Фронтенд (≈2–3 ч)
1. Экран входа и регистрации.
2. Каркас: список чатов слева, чат в центре, карта справа; мобильная вёрстка.
3. Чат: поток ответа, markdown, блок «Ход мысли» (размышления и шаги с временем), кнопка «Стоп», токены и цена.
4. Карта Leaflet: метки из события `places`, карточка места, подсветка при клике.
5. Подсказки-примеры в пустом чате, понятные сообщения об ошибках.

**Контрольная точка 4:** открываешь http://localhost:8000 и проходишь сценарии из раздела «Проверка всего MVP». Твои замечания по UX правлю до перехода к этапу 5. Коммит «Фронтенд: чат, ход мысли, карта».

### Этап 5. Доводка и сдача (≈1 ч)
1. `main()`: `uv run ai-course-agents` при необходимости строит индекс и запускает сервер.
2. Тесты pytest (см. раздел «Проверка»).
3. `README.md`: установка и запуск одной командой.
4. `docs/ARCHITECTURE.md`: схема, решения и компромиссы (DeepSeek, Qdrant, CPU, контекст, безопасность), раздел «что делал агент, что проверял я».
5. Проверка на чистом клоне: `git clone` → `uv sync` → `.env` → `uv run ai-course-agents`.

**Контрольная точка 5:** все тесты зелёные, чистый клон запускается. Коммит и push «MVP готов».

- `uv run ai-course-agents` → http://localhost:8000. Регистрируем двух пользователей в разных браузерах и проходим сценарии:

  5. Кнопка «Стоп» прерывает ответ; перезагрузка страницы восстанавливает историю чата.
- Журнал `data/runs/*.jsonl` содержит строки прогонов с токенами и ценой.
